A门槛为什么是 1024？

挖矿的额外开销是固定的，任务越小，占比越大。按理论估算，m = 1024 时约 25%；H100 实测远高于此。

单次挖矿乘法比普通乘法多花的时间（8B 最大的层 gate_up_proj）

m = 1024
理论 25%实测 +435%
m = 4096
理论 6%实测 +142%
m = 8192
理论 3%实测 +87%

m 是这一步的 token 数。理论值只算了给权重加噪声（2×128÷m）；实测还包括每次复制整份权重、算 Merkle 哈希和 CPU 端准备，小的层在 m = 1024 时慢到 13–19 倍。为什么正好是 1024，官方没有说明。

BPearl 为什么这么设计？

算法原理决定人不够技术不支持工程实现问题
  • 防偷工带来固定开销：噪声要在交出数据哈希之后才定。用户输入每一步都变，所以每一步都要对整份模型权重重新哈希、重新加噪声，这笔开销和这一步多大无关。
  • 和推理加速冲突：挖矿每一步都要在主机上取任务、提交结果，没法放进 vLLM 加速逐字生成用的 CUDA Graph。官方让整个服务关掉这项加速，实测每个 token 慢一倍。
  • 证明只支持 7 位整数乘法：约三分之一的计算格式不对，天生挖不了。

C对我们 PoCW 的启发

按任务摊薄开销
覆盖逐字生成
不看批大小
不碍推理加速
不设断崖门槛
  • 证明开销不能是"每一步的固定开销"，应该按任务摊薄。
  • 逐字生成、小批量、低负载时完成的有用工作，同样要能获得奖励。
  • 证明过程不能要求推理牺牲常规的加速手段。
  • 不能有"1023 不挖、1024 才挖"这种断崖，否则会诱导矿工凑批。
