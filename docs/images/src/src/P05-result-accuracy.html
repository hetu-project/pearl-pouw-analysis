PEARL 有用挖矿 · 问题 5 / 5

官方测试没真挖矿；我们补测：结果不变

官方用"开、关挖矿各生成一次，比较结果"来证明挖矿不影响结果。思路是对的，但测试提示太短，两次都没有真正挖矿。我们在 H100 上按正确方法补测了。

官方测试的流程 出问题的地方 我们的测法和结果

官方测试是怎么做的 test_vllm_execution.py 中的 test_consistency

01准备一条提示

例如"What is 2+2?"，最长的一条也只有 336 个 token。

02打开挖矿，生成一次

每次只发这一条，生成回答时每步只有 1 个 token。

03关闭挖矿，再生成一次

开关只改"走挖矿乘法还是普通乘法"，其他都不变。这一点设计得对。

两次都没挖
04比较两次的文本

都是"2 + 2 = 4"，测试通过。但没有一步达到 1024 个 token 的挖矿门槛，两次跑的是同样的代码。

A数据对不上的地方

  • 没挖矿：测试里也没有检查挖矿乘法有没有被调用过，所以一直没被发现。
  • 只比短答案："2 + 2 = 4"这种几个 token 的回答，就算真挖了也说明不了多少。
  • 其他数据补不上：计算库单元测试只测到 k = 8192；模型卡评测没说是否开着挖矿；8B 模型没有任何精度数据。

由代码证实：从 Pearl 源码和固定版本的模型卡中直接读出

B正确的验证方法

思路不变，开、关挖矿各跑一次，但要做到三点：

  • 保证真的挖了：一次提交大量请求，让每一步都 ≥ 1024 个 token；统计挖矿乘法的调用次数，开挖矿时必须大于 0，关挖矿时必须为 0。
  • 用评测集比准确率：GSM8K 全部 1319 道题，比较两次的准确率和每道题的答案。
  • 记录条件：模型、显卡、并发数、挖矿调用次数，让别人能重跑。

C我们的实测结果

1 张 H100、官方插件和官方 8B 模型，按左边的方法跑：

关挖矿
84.31%
开挖矿
84.31%

GSM8K 1319 题准确率

  • 生成文本 100% 逐字一致；开挖矿时挖矿乘法被调用 13,840 次，确认真挖了。
  • 单个矩阵乘法：挖矿版和普通版的输出逐位相同。
  • 对 PoCW：结果对不对要由协议验收；"做有用功不影响结果"要在证明真正执行的条件下测。
