# P02：有用挖矿覆盖率低，对话类负载下只有约 0–5% 的推理计算参与挖矿

**严重程度：严重** ｜ **结论：成立**（触发规则由代码证实；具体比例为 CPU 仿真估算，待 GPU 实测） ｜ Benchmark：[`benchmarks/P02-mining-coverage`](../../benchmarks/P02-mining-coverage)

## 一、问题是什么

P01 说明协议不强制"有用"。P02 进一步说明：**就算矿工自愿用 AI 推理来挖矿，绝大部分推理计算也根本不会进入挖矿。**

Pearl 官方的推理挖矿插件（vLLM 插件）只在一步处理的 token 数 m ≥ 1024 时才挖矿。对话场景中，绝大多数步是"一个一个往外生成字"的解码步，这时 m 等于同时在服务的用户数，通常远小于 1024，所以不挖。

结果是：聊天这类最主流的负载几乎不产生挖矿；只有"长输入、短输出"的负载（RAG、代码补全、长文档）才挖得多。

## 二、原来的算法是什么

### 1. 挖矿的触发规则

插件把推理中每一次线性层的矩阵乘法拿出来判断：满足条件才走挖矿用的带噪乘法（`pearl_gemm_noisy`），否则走普通乘法（`pearl_gemm_vanilla`），不挖。

| 内容 | 代码位置（Pearl `156ef9a8`） |
|---|---|
| 阈值：`min_m: 1024`、`min_n: 256`、`min_k: 1024` | `miner/vllm-miner/src/vllm_miner/config.yaml:9-12` |
| 判断函数 `should_use_noisy_gemm(m, n, k)`：三个维度都达到阈值才返回 true | `config.py:36-44` |
| 调用点：m = 这一步的 token 总数，n = 输出维度，k = 输入维度 | `vllm_kernels.py:204-208` |

**m 是什么？** vLLM 每一步把多个用户的请求拼在一起算，m 是这一步的 token 总数：
- **预填充（读用户输入）**：m = 这一步处理的输入 token 数。用户输入 500 个 token，m 就是 500；
- **解码（逐个生成回答）**：每个用户每步只生成 1 个 token，m = 同时在生成的用户数。10 个用户同时在聊，m 就是 10。

### 2. 哪些层能挖

只有 7 bit 量化的层能挖（`vllm_config.py:67-84`）。官方发布的模型中：

| 层 | 8B 模型 | 70B 模型 | 能不能挖 |
|---|---|---|---|
| `o_proj`（注意力输出） | 全部 32 层 | 全部 80 层 | 能 |
| `gate_up_proj`（前馈层前半） | 全部 32 层 | 全部 80 层 | 能 |
| `qkv_proj`（注意力输入） | 第 16–31 层能挖，第 0–15 层是 FP8 | 第 40–79 层能挖，第 0–39 层是 FP8 | 一半能 |
| `down_proj`（前馈层后半） | 全部 FP8 | 全部 FP8 | **不能** |
| `lm_head`（输出词表） | bf16 | bf16 | **不能** |
| 注意力计算（QKᵀ、PV） | 不经过插件 | 不经过插件 | **不能** |

所以，即使 m 足够大，线性层里能挖的计算也最多只有约 **67%**。

### 3. 官方自己也承认

Pearl 的 FP8 新分支 README（`origin/fp8-scheme:miner/vllm-miner/README.md`）写明，解码和小批量走普通乘法，挖矿只在预填充时进行，但没有给出比例。

## 三、我们怎么验证的

Benchmark 分两部分，**都在 CPU 上运行，没有使用 GPU**。

**第 1 部分：用 Pearl 自己的代码判断（代码实测，确定结果）**
- 不重写规则：直接加载 Pearl 插件的 `config.py` 和 `config.yaml`，调用它的 `should_use_noisy_gemm`；
- 各层的量化方式从官方模型在 Hugging Face 上的 `config.json` 读取（固定版本，校验 sha256）；
- 把 8B、70B 每一层的真实形状，配合不同的 m（1 到 8192）和不同张量并行度（TP=1/2/4/8）代进去，看哪些层会挖。

**第 2 部分：负载仿真（CPU 仿真估算）**
- 仿真程序在 CPU 上运行，**用 H100/H200 的公开规格参数**（算力、显存带宽、显存容量）估算每步耗时和显存能容纳的用户数，再模拟 vLLM 的调度：每步最多 8192 token、最多 1024 个用户、分块预填充、按显存准入；
- 模拟的配置：8B 模型 + 模拟 H100，70B 模型 + 模拟 H200；
- 6 种公开负载，输入、输出长度来自论文公开的统计数据：

| 负载 | 平均输入 | 平均输出 | 类型 |
|---|---|---|---|
| Alpaca | 19 | 58 | 短问答 |
| LMSYS-Chat-1M | 70 | 215 | 真实聊天 |
| ShareGPT | 161 | 338 | 真实聊天 |
| Azure 对话 | 1020（中位） | 129（中位） | 微软生产环境，长提示对话 |
| Azure 代码 | 1500（中位） | 13（中位） | 代码补全 |
| Mooncake/Kimi | 8590 | 182 | 长文档 |

- 请求率分 4 档，每档模拟 300 秒；
- 敏感性分析：每步固定开销 0 / 5 ms；前缀缓存命中率 50%。

**第 2 部分中有依据和是假设的内容**：
- 有依据：触发规则与可挖层（同第 1 部分）、H100/H200 公开规格、6 种负载的长度统计；
- 是假设：显卡实际效率按峰值的 60%（算力）和 80%（带宽）；长度分布取对数正态；请求随机到达；vLLM 调度按默认参数简化。

## 四、Benchmark 结果（第 1 部分为代码实测，第 2 部分为 CPU 仿真估算）

### 第 1 部分：m 达到多少才挖（代码实测）

被挖的乘加占线性层乘加的比例：

| m（一步的 token 数） | 1 | 8 | 64 | 256 | 512 | 1023 | **1024** | 2048 | 8192 |
|---|---|---|---|---|---|---|---|---|---|
| 8B | 0% | 0% | 0% | 0% | 0% | 0% | **67.3%** | 67.3% | 67.3% |
| 70B | 0% | 0% | 0% | 0% | 0% | 0% | **67.6%** | 67.6% | 67.6% |

- **m=1023 时一点都不挖，m=1024 时突然挖 67%**，中间没有过渡；
- 8B 用 8 卡张量并行（TP=8）时上限降到 59.6%：`o_proj` 被切开后 k=512，低于 1024，不再挖；
- 参考输出：[`results/reference-trigger-table.txt`](../../benchmarks/P02-mining-coverage/results/reference-trigger-table.txt)。

### 第 2 部分：真实负载下被挖的比例（CPU 仿真估算）

被挖的乘加 ÷ 全部推理乘加（含注意力和 lm_head）：

| 负载 | 8B / 模拟 H100 | 70B / 模拟 H200 |
|---|---|---|
| Alpaca | **0%** | **0%** |
| LMSYS 聊天 | **0–1.7%** | **0–1.9%** |
| ShareGPT 聊天 | **1.2–2.7%**（满载 64 请求/秒时 11.9%） | **0–5.3%** |
| Azure 对话（长提示） | 46–58% | 50–58% |
| Azure 代码 | 54–60% | 58–64% |
| Mooncake 长文档 | ≈51% | ≈57% |

- **前缀缓存**（vLLM 默认开启，多轮对话中重复的上文不再计算）：命中率 50% 时，ShareGPT 降到 **0–0.6%**（8B）和 **0–1.5%**（70B）；
- 每步固定开销改成 5 ms，结论不变；
- 参考输出：[`results/reference-workload-sim.txt`](../../benchmarks/P02-mining-coverage/results/reference-workload-sim.txt)。仿真用固定随机种子，重跑结果完全一致。

> 第 2 部分数据由仿真程序在 CPU 上计算得出，使用 H100/H200 公开规格参数和公开负载统计，**未在 GPU 上实测**。"对话类负载几乎不挖"这一结论主要由"解码时 m = 同时在聊的用户数"这条代码规则决定，对假设参数不敏感；具体百分比只能作为量级参考，待 GPU 实测确认。

### 哪些需要 GPU 实测

- **不需要实测**：触发规则、可挖层、"纯解码步不挖"。这三点由代码决定。
- **需要实测**：具体比例。仿真没有覆盖 vLLM 的真实抢占行为、挖矿开销与主计算的重叠、真实的多轮前缀命中率。
- 实测方案：1×H100 跑 8B、1×H200 跑 70B，使用官方 Docker 并加插桩，记录每次乘法的 (m, n, k) 和是否挖矿。约 20 GPU 小时，80–120 美元。

## 五、这个问题会影响什么

1. **最主流的负载几乎不挖**：聊天、问答是大模型最常见的用法。在这类负载下，即使矿工老老实实做推理，被挖的计算也只有 0–5%，"有用补贴"几乎为零。
2. **有用挖矿只在少数场景成立**：长输入、短输出（RAG、代码补全、长文档），而且需要较高并发。
3. **小矿工、低负载时完全不挖**：一张卡上只有几个用户时，解码 m 远小于 1024，预填充也很难凑够 1024，GPU 大部分时间空闲。官方软件这时不产生任何挖矿份额，而纯挖矿软件能 100% 占满 GPU。这直接引出 P03：有用挖矿比纯挖矿更不划算。
4. **阈值不是能随便调低的**：带噪乘法每次都要对整份权重做哈希和加噪，这部分固定开销在 m 小时占比很高（约 2r/m），所以阈值是这个设计本身的限制，不是参数没调好。新的 FP8 分支也延续了"只在预填充时挖"的设计。

## 六、Pearl 为什么这么设计

### 1. 为什么一步要 ≥1024 个 token 才挖：小任务的挖矿开销会超过推理本身

**PoUW 的初衷是挖矿只比推理多花一点点算力**（cuPOW 论文称额外开销为 1+o(1)）。但 Pearl 的挖矿额外开销是一笔与任务大小无关的固定开销，任务越小，它相对推理的占比越大。1024 就是官方为"额外开销占比"划的线。

- **固定开销从哪来**：防偷工要求噪声在矿工交出 A、B 的哈希之后才确定（P01 第六节）。插件每一步都按这个顺序执行（`miner/vllm-miner/src/vllm_miner/gemm_operators.py:68` 起）：对 A 算哈希 → 对 B 算哈希 → 生成噪声 → 给 A、B 加噪声并计算 → 去噪声。A 是这一步用户输入的中间结果，每一步都不同，所以每一步都要对整份权重 B 重新哈希、重新加噪声（代码注释："Always compute B noising (depends on A through EAR)"）。
- **它和任务大小无关**：给 B 加噪声的工作量只取决于权重大小，约为推理计算的 2r/m（r = 128，m 是这一步的 token 数，P03 第二节）。推理计算与 m 成正比，这笔开销不随 m 变化，所以 m 越小，占比越大：

| 一步的 token 数 m | 挖矿额外开销 ÷ 推理计算（2r/m） | 含义 |
|---|---|---|
| 10（10 个用户同时在生成回答） | 约 25 倍 | 算力主要花在挖矿上，推理反而成了零头 |
| 256 | 约 100% | 分界点：挖矿开销等于推理本身 |
| **1024（插件门槛）** | **约 25%** | 额外开销降到推理的四分之一 |
| 4096 | 约 6% | 接近 PoUW 的初衷 |

- **结论**：m 小于 256 时，挖矿的额外开销超过推理本身；m 在 256 到 1024 之间，额外开销仍占推理的 25%–100%，会明显拖慢 AI 服务。官方插件只在 m ≥ 1024 时挖，即只在额外开销不超过推理约四分之一时挖。对话生成回答时每一步只有几十个 token，额外开销是推理的几倍到几十倍，所以不挖，这就是对话类负载覆盖率只有约 0–5% 的原因。
- **说明**：表中只计入了给 B 加噪声的开销，对 B 做哈希等开销未计入，实际占比更高。1024 这个值从第一次提交（`960681d4`，2026-03-17）起写在 `config.yaml` 里，官方没有说明为什么选它；"按约 25% 的开销划线"是我们的推断。

### 2. 为什么对话负载几乎不挖：解码步天然很小，而且和推理加速机制冲突

- **解码步的 m 很小**：生成回答时，每个用户每步只出 1 个 token，m 等于同时在生成的用户数，通常远小于 1024（第二节）。
- **挖矿和 CUDA Graph 冲突**：vLLM 主要靠 CUDA Graph 加速解码，即把一步的 GPU 计算预先录下来，之后直接重放。挖矿每一步都要在主机上执行 Python 逻辑：读取当前的挖矿任务、中奖后异步回调提交区块（`gemm_operators.py` 中的 `get_mining_job`、`schedule_status_check`），重放录好的图不会再执行这些逻辑。
  - 官方的启动命令因此带了 `--enforce-eager`，整个 AI 服务都不用 CUDA Graph（`miner/vllm-miner/README.md:56`、`miner/README.md:129`）。
  - FP8 新分支改为开着 CUDA Graph，但 README 写明录好的图一律走不挖矿的普通计算，挖矿只在不录图的预填充步进行（`origin/fp8-scheme:miner/vllm-miner/README.md:186-187`）。
  - "冲突的原因是主机侧逻辑无法录进图里"是我们根据代码的推断，官方没有说明。
- 两点叠加，聊天这类以解码为主的负载几乎不挖。

### 3. 为什么最多只有约 67% 的线性层能挖：证明只支持 int7 乘法

- **协议只支持一种乘法**：证明的运算类型只有 `Int7xInt7ToInt32` 一种，注释写明"初版区块链只支持这一种"（`zk-pow/src/api/proof.rs:18-25`）。插件只把权重和输入都是 7 位量化的层当作挖矿层（`vllm_config.py:67-84`）。
- **哪些层量化成 7 位，由官方发布的模型决定**：官方模型把 `down_proj`、一半的 `qkv_proj` 留在 FP8，`lm_head` 留在 bf16（第二节）。代码和文档都没有说明原因，我们推断是为了保证推理精度。
- **注意力计算（QKᵀ、PV）不是"输入 × 权重"的形式**，不经过插件，也不能挖。

## 七、对我们的启发

1. **证明开销不能是"每一步的固定开销"**：Pearl 每一步都要对整份权重重新哈希、重新加噪声，开销与这一步的大小无关，小任务的开销因此超过推理本身。PoCW 的证明和记录开销应按任务摊薄，例如一个任务只做一次承诺，而不是每次矩阵乘法都重做。
2. **工作量证明要覆盖主流负载的主要计算形态**：推理中占主导的是解码（每步只有几十个 token）。PoCW 不能把"可证明的工作"限定在某种矩阵形状上。
3. **奖励不能依赖推理阶段或批大小**：解码、小批量、低负载时完成的有用工作，同样要能获得奖励。
4. **证明过程不能和推理加速冲突**：Pearl 挖矿每一步都要在主机上取任务、回调提交，官方因此让整个 AI 服务关掉 CUDA Graph。PoCW 的证明过程不能要求推理牺牲常规的加速手段，否则做有用功的人要付出服务性能的代价。
5. **避免断崖式规则**：1023 个 token 不挖、1024 个 token 就挖，会诱导矿工为了凑批而推迟或合并请求，损害服务质量。奖励应随有用工作量平滑变化。
