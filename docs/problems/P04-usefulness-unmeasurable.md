# P04："有用"没有任何度量，在现行协议下也无法度量；主网抽样中 0 个区块符合官方有用挖矿软件的特征

**严重程度：严重** ｜ **结论：成立**（协议层面不可度量由代码证实；链上形状普查为真实数据实测） ｜ Benchmark：[`benchmarks/P04-usefulness-unmeasurable`](../../benchmarks/P04-usefulness-unmeasurable)

## 一、问题是什么

Pearl 的核心卖点是"挖矿即有用的 AI 计算"。但是：

1. **官方没有公布任何"有用挖矿占多少"的数据**，链上也没有这类指标；
2. **在现行协议下，这个比例根本无法度量**：链上看不到矩阵内容，协议里没有"用户""请求""交付"这些概念，外部任何人都无法证明或证伪"某个区块做了有用计算"；
3. 我们用唯一能拿到的公开信息，即每个区块证书里的挖矿参数，对主网做了一次"形状普查"：**抽样的 913 个区块中，0 个符合官方有用挖矿软件的特征**。主网矿工用的几乎都是 n=131072、262144 这类远大于任何 AI 模型层宽度的矩阵，是专为挖矿设计的形状。

## 二、原来的算法是什么

### 1. 链上能看到什么

每个区块都带一份证书（`node/wire/certificate.go`），结构为：

```
版本(4) | 区块哈希(32) | 公开数据长度(4) | 公开数据(164) | 证明长度(4) | 零知识证明(59,560)
```

其中公开数据只有 164 字节（`zk-pow/src/api/proof.rs:78-80`）：

| 字段 | 字节 | 含义 |
|---|---|---|
| 挖矿配置 | 52 | k、噪声秩 r、运算类型、行图样、列图样、MoE 参数 |
| hash_a、hash_b | 32 + 32 | 矩阵 A、B 的 Merkle 根 |
| hash_jackpot | 32 | 彩票哈希 |
| m、n | 4 + 4 | 矩阵尺寸 |
| t_rows、t_cols | 4 + 4 | 中奖小块的位置 |

### 2. 为什么协议层面无法度量"有用"

| 原因 | 说明 |
|---|---|
| **矩阵内容不可见** | 链上只有矩阵的 Merkle 根和尺寸；被打开的 h 行、w 列是零知识证明的私有输入，链上看不到（P01）。外部观察者无法对矩阵做任何统计检验 |
| **协议里没有需求方** | 协议中没有"请求""用户""签名的推理任务""交付输出"这类对象；去噪后的结果 C 从不出现在协议中，无从知道它是否交付给了任何人 |
| **激活矩阵 A 可以自己造** | 即使公开 A，矿工也可以自己给自己发请求，或者合成输入。没有第三方签名，"是否服务了真实用户"在原理上无法判定 |
| **用模型权重当 B 也不能说明有用** | 理论上可以把 hash_b 和公开的模型权重比对，但纯矿工完全可以用公开权重当 B、配随机 A 挖矿（P03：B 每个区块只需加噪一次）。"B 是模型权重"只是有用的必要条件，不是充分条件 |

### 3. 唯一能做的：用挖矿参数给出上界

官方有用挖矿软件（vLLM 插件）产生的区块，挖矿参数有固定特征。不符合这些特征的区块，**一定不是**有用挖矿挖出来的：

| 条件 | 依据（Pearl `156ef9a8`） |
|---|---|
| S1 噪声秩 r = 128 | `miner/miner-base/src/miner_base/settings.py`：`noise_rank = 128` |
| S2 小块图样：行 [0, 8]，固定的 64 列 | 同上：`rows_pattern`、`cols_pattern` |
| S3 不是 MoE | 主网 91630 高度起禁用 MoE |
| S4 m ≥ 1024 | `miner/vllm-miner/src/vllm_miner/config.yaml`：`min_m = 1024`（P02） |
| S5 n 和 k 都等于官方模型的某个层宽度（可除以张量并行度 1/2/4/8） | 4 个官方模型的 `config.json` |

全部满足的区块也只是"可能有用"，因为纯矿工可以模仿这些参数。所以普查结果是有用挖矿比例的**上界**。

## 三、我们怎么验证的

**1. 外部事实（2026-10-27/28 核对）**
- 官方没有公布有用挖矿比例。TechFlow 转述核心开发者的说法：链上没有度量有用挖矿比例的指标；cuPOW 论文作者 Weinstein 在采访中也承认，矿工自选矩阵的设计本身就允许垃圾挖矿，并表示将来的升级会让垃圾挖矿的激励趋近于零，但没有给出时间表。
- Together AI 2026-05-15 宣布与 Pearl 合作，但其 Pearl 模型页面至今（2026-10-28 复核）仍显示 "Launching soon"，并注明该模型不在 Together 的 Serverless API 上提供。
- Basu 论文对主流第三方挖矿软件做了字符串和显存分析，没有发现推理代码（作者自认证据是提示性的，不是决定性的）。

**2. 链上形状普查（真实数据实测，只在 CPU 上运行）**
- 数据来源：PRL Labs 运营的公开区块浏览器（Blockbook），读取主网原始区块，按 Pearl 的格式解析证书中的公开数据。只读公开数据，不向网络发送任何交易，只保存解析出的参数，不保存证明；
- 样本：V3 证书启用（高度 99000）之后，每 50 块取 1 块，加上最新的连续 200 块，共 **913 个区块**（高度 99000–134800，时间 2026-08-11 至 2026-10-28）；
- 检查：逐块检查 S1–S5。r 和图样直接从 Pearl 源码的 `MinerSettings` 读取，不手抄；S5 故意放宽，四个官方模型（Llama 8B、Llama 70B、Gemma 31B、Qwen3 30B）所有线性层的输入、输出宽度都算，n 和 k 可以取其中任意值，放宽只会让上界更高。

## 四、Benchmark 结果（真实链上数据）

### 1. 逐条检查

| 条件 | 单独满足 | 累计满足 |
|---|---|---|
| S1 r = 128 | 913（100%） | 913（100%） |
| S2 官方小块图样（2×64） | 64（7.0%） | 64（7.0%） |
| S3 不是 MoE | 913（100%） | 64（7.0%） |
| S4 m ≥ 1024 | 908（99.5%） | 64（7.0%） |
| S5 n、k 都是模型层宽度 | 24（2.6%） | **0（0%）** |

**913 个区块中，0 个可能来自官方有用挖矿软件。按 95% 置信度，有用挖矿占比的上界为 0.42%。**

- 用了官方 2×64 图样的 64 个区块，矩阵尺寸都是 n=131072、262144、524288 这类远超模型层宽度的值，说明有矿工沿用了官方的图样参数，但做的是纯挖矿；
- n、k 恰好落在模型层宽度上的 24 个区块，小块图样都不是官方的（如 16×16、10×16），也不是官方有用挖矿软件产生的；
- 有 5 个区块的 m 只有 512 或 768，低于官方插件的 1024 阈值。

### 2. 主网矿工实际在用的形状

| 参数 | 分布 |
|---|---|
| n（B 的列数，对应模型输出维度） | 中位数 **131072**，最大 16,777,216；只有 6.2% 的区块等于某个模型层宽度。官方模型最大的层宽度是 57344 |
| m（一次计算的 token 数） | 中位数 8322，最大 16,777,216 |
| k（公共维度） | 8192（43%）、65536（17%）、32768（11%）、2048（11%）、4096（9%）、16384（8%） |
| 小块 h×w | 8×16（56%）、10×16（17%）、8×32（10%）、2×64（8%）、16×16（6%） |
| 噪声秩 r | 全部为 128 |
| 证明大小 | 全部为 59,560 字节 |

最常见的参数组合（前 5 名）：

| k | 小块 | m | n | 区块数 |
|---|---|---|---|---|
| 8192 | 8×16 | 4097 | 262144 | 58（6.4%） |
| 32768 | 10×16 | 5121 | 262144 | 40（4.4%） |
| 8192 | 8×16 | 16384 | 524288 | 36（3.9%） |
| 8192 | 8×32 | 16384 | 65536 | 30（3.3%） |
| 16384 | 8×16 | 8192 | 131072 | 29（3.2%） |

这些都是为了挖矿效率自选的形状：n 越大，A 的加噪开销 2r/n 越小（P03）；k 取 65536 是协议允许的最大值。

完整输出：[`results/reference-census.txt`](../../benchmarks/P04-usefulness-unmeasurable/results/reference-census.txt)；样本数据：[`results/certs-mainnet.jsonl`](../../benchmarks/P04-usefulness-unmeasurable/results/certs-mainnet.jsonl)（每行一个区块的高度、时间、哈希和公开参数，可以对照区块浏览器逐块核对）。

### 3. 局限

- **这是上界，不是精确值**：满足全部条件的区块也只是"可能有用"。本次结果是 0，上界由样本量决定（913 块 → 0.42%）；
- **只覆盖官方有用挖矿软件**：如果有人自己写了一个用其他参数的有用矿工，普查认不出来。但目前没有任何公开的第三方有用挖矿软件；
- **是抽样**：每 50 块取 1 块，加最新的 200 块。全量普查需要读取约 3.6 万个区块（约 2 GB），方法相同，可以用 `p04_fetch_certs.py` 调小步长完成。

## 五、这个问题会影响什么

1. **核心卖点无法被证实，也无法被证伪**："挖矿即有用的 AI 计算"既没有官方数据支撑，也不能被任何外部方验证。投资者、矿工和用户无法依据数据评估"有用"的程度。
2. **现有证据都指向有用比例接近零**：本次普查中 0 个区块符合官方有用挖矿软件的特征；Together AI 的端点至今未上线；Basu 在主流挖矿软件中没有发现推理代码。
3. **项目方说什么都无法核对**：即使将来官方公布一个"有用比例"，在现行协议下外界也无法核对它。
4. **形状普查是目前唯一的外部度量方法**：它只能给出上界，而且一旦纯矿工开始模仿官方参数，这个上界就会失效。

## 六、对我们的启发

1. **"有用"必须是协议内可度量的量**：每一份被奖励的工作都应在链上留下可审计的记录，包括它对应哪个需求、由谁发起、结果是否被验收。有用比例应该能直接从链上统计出来，而不是依赖项目方的声明。
2. **协议里要有需求方**：需求方（用户或其代理）对任务签名，执行方对交付签名，验证方对验收签名。有了这条因果链，"是否服务了真实用户"才可以判定。
3. **不能只靠参数特征判断有用**：Pearl 的参数特征（矩阵形状、图样）可以被纯矿工模仿。PoCW 的有用性判定必须依赖不可伪造的信息（需求方签名、交付证明），而不是可以照抄的配置。
4. **公开度量数据和复现方法**：PoCW 上线后，应从第一天起公布有用工作比例等指标，并提供任何人都能重跑的统计脚本，就像本仓库的普查脚本一样。
