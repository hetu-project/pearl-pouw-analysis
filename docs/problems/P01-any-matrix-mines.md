# P01：任意矩阵都能挖矿出块，包括全零矩阵

**严重程度：致命** ｜ **结论：成立（本机实验证实）** ｜ Benchmark：[`benchmarks/P01-any-matrix`](../../benchmarks/P01-any-matrix)

## 一、问题是什么

Pearl 宣称矿工挖矿用的是 AI 推理里的矩阵乘法，所以挖矿是"有用"的。

但 Pearl 的验证者**根本不检查矩阵是不是来自 AI 推理**。我们用**随机数、全零、全是同一个常数**的矩阵挖矿，生成的区块都通过了 Pearl 完整的共识验证。

也就是说，"有用"在协议里**无法验证，也无法强制**。

## 二、原来的算法是什么

完整算法与参数说明见 [`docs/pearl-algorithm.md`](../pearl-algorithm.md)。

### 1. 矿工挖矿

1. 矿工自己选两个矩阵 A（m×k）和 B（k×n），元素是 −64 到 64 之间的整数；
2. 对 A、B 分别算 Merkle 根，作为承诺；
3. 由区块头和两个承诺推导出随机种子，生成低秩噪声 E_A、E_B；
4. 计算 (A+E_A)×(B+E_B)，把结果切成很多 h×w 的小块，每个小块算一张"彩票"；
5. 彩票的哈希值小于难度目标就算中奖。矿工交出中奖小块用到的 **h 行 A、w 列 B**，以及它们的 Merkle 路径。

### 2. 验证者检查什么

验证函数 `verify_plain_proof`（`zk-pow/src/api/verify.rs:101-134`）一共 6 步：

| 步骤 | 检查内容 | 代码位置 |
|---|---|---|
| ① | 解析证明，核对 h 行、w 列的 Merkle 路径是否对得上承诺 | `:108` |
| ② | 检查参数（矩阵尺寸、噪声秩、小块大小）是否在允许范围内 | `:111` |
| ③ | **检查每个元素是否在 [−64, 64] 之间** | `:114-118` |
| ④ | 由种子重新生成噪声 | `:124` |
| ⑤ | 用这 h 行、w 列重算中奖小块的彩票 | `:127` |
| ⑥ | 算彩票哈希，和难度目标比较 | `:130-131` |

**关键在于：对矩阵内容唯一的检查是第 ③ 步"数值在 [−64, 64] 之间"。** 除此之外，没有任何一步检查矩阵是不是真实数据、有没有统计特征、是不是来自某个模型。

另外两点：
- **验证者只重算一个小块**：节点默认配置下占整个矩阵乘法的 1/4096；按大模型的真实尺寸（m=n=4096）约为百万分之八。
- **有用的输出（去噪后的 A×B）从来不出现在验证里**：不提交、不发送、不检查。

区块上链用的是零知识证明，链上公开的数据只有 164 字节：配置、两个承诺、彩票哈希、矩阵尺寸、小块坐标（`zk-pow/src/api/proof.rs:78-80`）。**链上连那 h 行、w 列的数据都看不到。** 共识层额外的检查（`node/blockchain/validate.go:529-560`）只看证书版本、是否禁用 MoE、秩惩罚，也不看矩阵内容。

### 3. 附带发现：官方参考挖矿函数本身就不算乘积

Pearl 自带的 CPU 挖矿函数 `try_mine_one`（`zk-pow/src/ffi/mine.rs:18-129`）：
- 用**随机数**生成 A 和 B（`:33-40`）；
- 逐个小块算彩票，中奖就直接返回（`:108-125`）；
- **从来不计算完整的 A×B，也不去噪，不输出任何结果**。

也就是说，Pearl 官方维护的这个实现，本身就是一个"合规但没有任何用处"的矿工。

## 三、我们怎么验证的

**实验环境**
- 代码：Pearl `156ef9a8`（主网当前版本），未做任何修改；实验程序作为 example 复制进 `zk-pow/examples/` 后编译；
- 机器：Apple M4、16 GB 内存；Rust 1.88.0；
- 实验程序：[`benchmarks/P01-any-matrix/p01_any_matrix.rs`](../../benchmarks/P01-any-matrix/p01_any_matrix.rs)。

**实验参数**（节点默认配置）
- 矩阵尺寸 m=256、n=512、k=2048；噪声秩 r=128；小块 4×8；
- 种子方式：V3（加盐种子，主网当前规则）；
- 难度 nbits=0x1E01FFFF（节点测试用的低难度，为了几秒内出结果）。

**4 组测试矩阵**

| 组 | 矩阵内容 | 生成方式 |
|---|---|---|
| 1 | 随机数，范围 [−64, 64] | `mine()` 默认参数 |
| 2 | **全零** | `signal_range=(0,0)` |
| 3 | 全部是 7 | `signal_range=(7,7)` |
| 4 | 全部是 −64 | `signal_range=(-64,-64)` |

**每组都走完 Pearl 的 5 道检查，也就是一个区块上链要过的全部关卡：**
1. `mine()`：用 Pearl 自己的挖矿函数挖出一个中奖小块；
2. `verify_plain_proof`：原始证明验证，矿池验份额用的就是这个；
3. `check_cert_version_eligible(3)`：证书版本检查；
4. `zk_prove_plain_proof` → `verify_block`：生成零知识证明，再用**节点共识路径**验证；
5. `check_rank_penalty`：秩惩罚检查。

- 4 组共耗时 21.3 秒，内存峰值约 4.2 GB（常驻）/ 5.5 GB（峰值占用）；
- 日志里可以看到全零那一组实际提交的矩阵数据：`[0, 0, 0, 0, 0, 0, 0, 0, ...]`，照样通过；
- 挖矿结果是确定的：重跑时各组的 Merkle 根、中奖小块坐标与参考日志完全一致，只有耗时不同；
- 参考日志：[`benchmarks/P01-any-matrix/results/reference-apple-m4.log`](../../benchmarks/P01-any-matrix/results/reference-apple-m4.log)。

**关于难度**：实验用了低难度，但这不影响结论。难度检查只比较"彩票哈希 vs 目标值"，和矩阵内容无关；高难度下，全零矩阵和随机矩阵的中奖概率一样，只是要多算一会儿。

**和已有报道的区别**：Basu 论文（见 [`docs/references.md`](../references.md)）报道过"随机矩阵能被接受"，但只验证到原始证明和矿池份额。全零、常数矩阵走完包括零知识证明和节点共识在内的完整流程，以及官方参考挖矿函数本身不计算乘积，据我们所知此前未见公开报道。

## 五、这个问题会影响什么

1. **"有用挖矿"只是矿工的自愿行为，协议没有任何约束力**：任何人用随机数或全零矩阵挖矿，拿到的出块权和真正做 AI 推理的矿工完全一样。
2. **现实中大部分算力就是这么挖的**：Basu 论文发现最大矿池的主流挖矿软件里没有任何推理代码；全网约 96% 是消费级显卡加第三方纯挖矿软件（官方的有用挖矿软件只支持 H100/H200）。
3. **Pearl 的核心卖点不成立**："挖矿的同时完成 AI 推理"无法被任何人验证。即使有矿工真的做了推理，链上也分辨不出来。
4. **加大抽样也解决不了**：就算把验证范围扩大到整个矩阵，验证的仍然是"带噪声的乘法算没算对"，而不是"这个乘法是不是在为真实用户服务"。问题不在抽多少，而在于**"有用"这个属性根本不在验证对象里**。

## 六、Pearl 为什么这么设计

**结论：这不是代码 bug，是有意的取舍。** Pearl 要做"无许可"的共识，矿工自己选矩阵，网络不派任务。为此它把"有用"定义成"想做有用计算的矿工几乎不吃亏"，而不是"网络保证每次挖矿都有用"。在这个定义下，全零矩阵能出块是预期行为。

标注约定：**【论文】** 指 cuPOW 论文 arXiv:2504.09971v4；**【白皮书】** 指 Pearl FP8 白皮书（2026-09）；**【代码】** 指 Pearl `156ef9a8`；**【推断】** 指我们的推断。资料链接见 [`docs/references.md`](../references.md)。

### 1. 设计目标：无许可，矿工自己选输入

- 【论文】摘要开宗明义，要在"矿工自己选择输入"（*the miner itself chooses the input x*）的无许可环境里实现基于真实计算的工作量证明。
- 【论文 §1】作者把"由矿工而不是网络选择要算的实例"作为和以往方案的根本区别；PoUW 的形式定义（Definition 5.1）要求对**任意输入**都成立。
- 【推断】为什么坚持矿工自选：如果由网络派发任务，就需要一个"派任务的人"决定什么是有用的、并验收结果。这个角色就是一个信任点，和比特币式的无许可共识冲突；而在通用场景下高效验收任意任务的结果，以往没有可行方案（论文引用 Buterin 2019 年的观点，认为有用工作量证明"很可能不可行"）。

### 2. 论文里的"有用"是什么意思

论文给"有用"列了三条标准（§1），cuPOW 只在协议里保证其中两条：

| 论文的标准 | 含义 | cuPOW 怎么满足 | 协议是否强制 |
|---|---|---|---|
| 经济价值 | 计算结果有人愿意付钱 | 论证"矩阵乘法是 AI 的瓶颈，有人需要"，是**任务类型**层面的论证；§2 明确说概述里"忽略矩阵乘法的经济价值" | **否** |
| 效率 | 有用矿工几乎不多花成本 | 低秩噪声，去噪开销 1+o(1) | 理论上是（P03 说明实际上不成立） |
| 安全 | 不能少算却被接受 | 噪声 + 对计算过程做哈希抽签 | 是（基于未证明的假设） |

所以在 Pearl 的设计里，"有用"是"矿工**可以**用自己的有用计算来挖、几乎不吃亏"，不是"每一次挖矿**必须**有用"。

### 3. 全零矩阵能出块，在设计里是预期行为

- **噪声的作用是防偷工，不是防无用**：加上由区块决定的随机噪声后，不管矿工选什么矩阵，都得把带噪声的乘法完整算一遍才能刮彩票。
- 【论文 §1.1】作者把"全零矩阵和其他任何矩阵一样难算"写进贡献列表，当作安全性的体现，而不是漏洞。
- 【白皮书 §1】FP8 新方案重申了同一点：全零矩阵和其他矩阵一样难。
- 所以从 Pearl 的角度看，用全零矩阵挖矿没有"偷工"，只是"无用"。协议只防前者。
- 我们对计算层的分析也印证了这一点：全零矩阵在纸面上能少做约 17% 的乘加，但在 GPU 的 int8 张量核上没有任何加速。
- 第 ③ 步的数值范围检查也不是"有用性检查"。【代码】`zk-pow/src/api/verify.rs:113` 的注释说明它是为了和零知识电路的范围检查保持一致，即保证数据是 7 位整数格式。【推断】这样加上噪声后仍能放进 int8 张量核计算。

### 4. 为什么只验证一个小块

- 【论文 Remark 2.1】论文建议把每个中间小块的计算过程单独哈希，各算一次抽签机会；Pearl 采用了这个思路的变体：**一张彩票就是一个小块**。
- 中奖的那张彩票只用到 h 行 A 和 w 列 B，验证者重算这一个小块，就足以证明"这张彩票是真刮出来的"。
- 【论文 Alg 6.2】论文原始的验证方式是重算全部过程，成本和挖矿相当。全网每个节点都要验证每个区块，这不可接受。
- 所以抽一个小块是为了让验证便宜。这对"防偷工"足够，但和"有没有用"无关：有用的输出（去噪后的结果）根本不在这个小块里。

### 5. 为什么链上连那几行数据都看不到

- 【论文 Remark 2.2】验证太贵可以用 SNARK 委托；如果需要保护 A、B 的隐私，就用零知识 SNARK。
- 【代码】Pearl 主网证明的最后一层开启了零知识模式（`zk-pow/src/circuit/pearl_circuit.rs:273`，`build_recursion_config(..., 2, true)` 即 `zero_knowledge: true`），并专门对数据做了混淆（`pearl_trace.rs:147`）。
- 好处有两个：做 AI 服务时，A 是用户输入的中间结果，B 是模型权重，不公开就不会泄露用户数据和私有模型；证明大小固定为 59,560 字节，比直接公开那些行列和 Merkle 路径小得多。
- 代价是链上没人能看到矩阵，"有用"从原理上就无法从链上判断（P04）。

### 6. Pearl 靠什么让矿工做有用功：经济激励

- 【论文 摘要】逻辑是：有用矿工几乎不多花成本，本来就要做矩阵乘法的人（AI 训练和推理）会顺便挖矿，一份算力拿两份收益（*2-for-1*）。
- 【白皮书 §6】"诚实矿工"被定义为用"本来就想算的乘法"挖矿的矿工。
- 【白皮书 §7】白皮书承认，不要求结果可用的矿工可能获得加速；FP8 方案新增的统计检查只用来限制这种**加速**，不判断有没有用。
- 论文作者 Weinstein 在采访中承认这个设计允许垃圾挖矿，并表示将来的升级会让垃圾挖矿的激励趋近于零，但没有给出方案和时间表（见 [P04](P04-usefulness-unmeasurable.md)）。
- 这个激励能不能成立，取决于"有用挖矿真的几乎不多花成本"。P02、P03 说明在实际实现里不成立：覆盖率低，有用挖矿的收益只有纯挖矿的 44–61%。结果就是 P04 测到的：主网抽样中 0 个区块符合官方有用挖矿软件的特征。

### 7. 设计链条

| 层次 | 内容 | 依据 | 性质 |
|---|---|---|---|
| 目标 | 无许可，矿工自己选输入，网络不派任务 | 论文摘要、§1、Definition 5.1 | 有意选择 |
| 推论 1 | 协议不知道什么是"有用"，所以不检查有用，只防偷工 | 论文 §1–2；`verify.rs:101-134` | 有意选择 |
| 推论 2 | 噪声让任何矩阵一样难算，所以全零矩阵也合规 | 论文 §1.1；白皮书 §1 | 有意选择，作者视为特性 |
| 推论 3 | 只验证中奖的那个小块，让验证便宜 | 论文 Remark 2.1、Alg 6.2；`verify.rs` | 工程取舍 |
| 推论 4 | 零知识证明隐藏矩阵，链上看不到数据 | 论文 Remark 2.2；`pearl_circuit.rs:273` | 工程取舍（隐私、证明体积） |
| 依赖的假设 | 有用靠经济激励：有用矿工几乎不吃亏，AI 用户会顺便挖 | 论文摘要；白皮书 §6–7 | 假设，P02、P03、P04 显示不成立 |

**所以 P01 修不掉**：只要坚持"矿工自选输入、协议里没有需求方"，就一定能用任何矩阵挖矿。FP8 新方案也没有改变这个前提。要让"有用"可以验证，就必须在协议里引入需求方，这正是 PoCW 的出发点，也是它要付出的代价。

## 七、会被追问的问题

**Q1：这是 bug 吗？Pearl 能修吗？**
不是 bug，是设计取舍（见第六节）。要修，就得放弃"矿工自选输入"、在协议里引入需求方或任务来源，那等于换一个协议。FP8 新方案也没有这样做。

**Q2：加一个"矩阵像不像模型权重"的检查不就行了？**
有两个障碍。第一，链上看不到矩阵（零知识证明）。第二，即使看得到，纯矿工也可以直接拿公开的模型权重当 B、随便造 A（P03、P04），照样能通过。这种检查只能判断"像不像"，判断不了"有没有人要"。

**Q3：多验证几个小块，甚至验证整个矩阵，能解决吗？**
不能。验得再多，证明的也只是"带噪声的乘法算对了"。有用的输出（去噪后的结果）不在验证范围里，也不交给任何人。

**Q4：用全零矩阵挖矿更便宜吗？算作弊吗？**
不更便宜，噪声保证了工作量相同；在 GPU 上也没有加速。所以它不是作弊，而是"合规的无用功"。这恰好说明 Pearl 防的是偷工，不是无用。

**Q5：那 Pearl 靠什么保证有用？**
不保证，靠激励：它假设有用挖矿几乎不多花钱，AI 用户会顺便挖。P02、P03 说明这个假设在实际实现里不成立，P04 的链上普查也没有找到有用挖矿的痕迹。

**Q6：为什么不让网络派发 AI 任务？**
那需要一个可信的派单方和验收方，违背了无许可的目标；论文正是把"矿工自选实例"当作主要贡献。PoCW 的选择是接受这一点信任（需求方签名、验证方验收），换取可以验证的有用性。

**Q7：官方 CPU 挖矿函数用随机矩阵，能说明什么？**
它是参考实现和测试工具，本身不代表官方的意图。但它说明，协议从设计上就接受不产生任何有用结果的挖矿，而且官方自己的代码就是这样挖的。

## 八、对我们的启发

1. **"有用"必须是验证对象本身**：要承诺"有用"，验证的对象就必须和**真实的需求、真实的输出**绑定，不能只验证矿工自选输入的中间计算结果。
2. **工作要挂在需求上**：每一份工作量都应能追溯到一个真实存在、由需求方发起的任务，以及需求方或验证者对结果的验收。没有需求来源的计算，不应获得奖励。
3. **随机抽查不能代替结果验证**：抽查一个小块只能证明"算了"，证明不了"算的是用户要的东西"。验证应检查最终交付给用户的输出（或其可检验的承诺），而不只是中间过程。
4. **对应的设计要求**：PoCW 用"因果绑定"解决这个问题，即份额必须挂在已验收的需求上（需求 → 执行 → 验收的因果链），没有因果来源的份额无效。
5. **要正视引入需求方的代价**：Pearl 不引入需求方，是为了不设信任点（第六节）。PoCW 引入需求方后，必须回答 Pearl 回避掉的问题：需求方可以自己给自己下单刷量。所以发起任务要付费或押金，验收要由独立的验证方打分，让刷单算下来不划算；否则只是把"矩阵随便选"换成了"需求随便造"。
6. **隐私和可验证性要分开处理**：Pearl 用零知识证明同时藏起了用户数据和"有没有用"。PoCW 应该只藏内容（输入、输出本身），公开需求签名、交付哈希和验收结果，这样既保护隐私，又能统计有用比例。
